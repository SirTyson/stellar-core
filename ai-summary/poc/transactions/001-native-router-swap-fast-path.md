# H001: Native Two-Token Soroswap Router Swap Fast Path

**Date**: 2026-05-23
**Subsystem**: transactions, Soroban apply bridge
**Severity**: High
**Impact**: soroswap apply-time reduction by bypassing the remaining router Wasm invocation
**Hypothesis by**: gpt-5.5, high

## Expected Behavior

For the apply-load soroswap workload, each accepted transaction invokes the router contract function `swap_exact_tokens_for_tokens` with the fixed two-token path shape built in `src/simulation/ApplyLoad.cpp:3427-3439`. The apply path should produce exactly the same ledger writes, authorization checks, contract events, return value, budget/resource accounting for the next protocol, and transaction meta as executing the router Wasm normally. The efficient expected behavior is to recognize this next-protocol-only shape during `InvokeHostFunctionOpFrame` execution and dispatch to a deterministic native implementation instead of instantiating and entering the router Wasm VM once per transaction.

## Mechanism

The current apply path still pays one full Wasm invocation per swap after the accepted native pair/pool optimizations: C++ serializes the host function into the Rust bridge in `InvokeHostFunctionOpFrame::invokeHostFunction`, Rust calls `Host::invoke_function`, and `Vm::invoke_function_raw` marshals arguments and executes the router Wasm. In the current trace, `Vm::invoke_function_raw` has 7,867 apply-overlapping events for 7,891 swap applications, which is effectively one VM call per transaction. A protocol-gated native router dispatch for the exact two-token `swap_exact_tokens_for_tokens` shape should remove most of the router Wasm instantiation/dispatch/marshalling cost while preserving deterministic execution order inside each transaction; it does not add parallelism and therefore does not exceed `NUM_CLUSTERS`.

### Trace Summary

`ApplyLoad::generateSoroswapSwaps` builds a single-op Soroban transaction whose top-level `HostFunction::InvokeContract` calls the Soroswap router with a two-token path and a source-account auth tree for the inbound SAC transfer. In p23+ apply, `TransactionFrame::parallelApply` dispatches the single operation through `OperationFrame::parallelApply` to `InvokeHostFunctionOpFrame::doParallelApply`, whose helper loads footprint entries, serializes the host function/auth/resources into Rust, and invokes the host. On the Rust side, `e2e_invoke::invoke_host_function` reconstructs storage/auth/source state and calls `Host::invoke_function`, which converts the `InvokeContract` args and reaches `call_contract_fn`; because the router instance executable is `ContractExecutable::Wasm`, the code instantiates a VM and always enters `Vm::invoke_function_raw`. The existing module cache can avoid reparsing/relinking some module state, but it does not avoid per-transaction VM creation, arg marshalling, or the Wasm/host dispatch boundary.

### Findings

The inefficiency exists. For any contract instance whose executable is `ContractExecutable::Wasm`, `Host::call_contract_fn` unconditionally instantiates a `Vm` and invokes `Vm::invoke_function_raw`; the current tree has no Soroswap-router fast path and no generic code-hash native dispatch. The module cache in `instantiate_vm` mitigates parsed-module/linker work but still leaves per-transaction VM construction, Wasm arg marshalling, and Wasm/host dispatch.

The inefficiency is on the soroswap hot path. The generated benchmark transaction shape reaches this path once per accepted swap, and the cited timestamp-filtered trace places `Host::invoke_function`, `Vm::invoke_function_raw`, and VM dispatch events inside `applyLedger` windows. After dividing worker aggregate time by `T=8`, the VM raw-call surface alone is about 20% of measured apply time; even a partial native router path has enough addressable budget to clear the objective's 3% Medium floor, and the full exact-shape path is High-tier.

The proposed fix is correctness-preserving only if it is implemented as a protocol-gated host-side native contract dispatch, not as a C++ bridge shortcut or a function-name-only benchmark shortcut. The branch must prove it is executing the exact intended router code/shape, preferably by matching the router Wasm hash and required function/argument/auth/footprint invariants before falling through to Wasm for everything else. It also must push an authorization/call frame equivalent to the router contract frame; otherwise the source-account auth tree will not match the downstream SAC `transfer` `require_auth` semantics. Keeping the fast path inside Rust Host execution allows the existing storage rollback, event extraction, result encoding, rent/refund accounting, and C++ `recordStorageChanges`/`collectEvents`/`finalizeSuccess` machinery to remain authoritative.

Correctness constraints are significant but not blockers at review stage. A valid PoC must reproduce the two-token router semantics: deadline and amount checks, pair-address/reserve logic, inbound SAC transfer authorization, outbound transfer/event order, pair reserve update, return vector, and error behavior. Budget charges may be intentionally repriced only under the next-protocol gate; for current protocol behavior, this would not be safe because budget consumption is consensus-visible.

### PoC Guidance

- **Target code**: Add the dispatch in `src/rust/soroban/p26/soroban-env-host/src/host/frame.rs`, most naturally in or just before the `ContractExecutable::Wasm` arm of `Host::call_contract_fn`; place the substantial native implementation in a new Rust module under `soroban-env-host/src/` or `builtin_contracts/`. Avoid changing `src/transactions/InvokeHostFunctionOpFrame.cpp` except for any unavoidable bridge plumbing; the C++ bridge/output path should remain unchanged.
- **Change description**: Under a next-protocol gate, recognize only the exact Soroswap router Wasm/code identity plus `swap_exact_tokens_for_tokens` two-token argument shape and required auth semantics, then execute the router swap natively through Host storage/event/auth APIs. Fall through to normal Wasm on any mismatch. Add or reuse a frame representation so the native router appears as the router contract to the authorization manager, similar in spirit to the existing `StellarAssetContract` native branch but keyed by the router Wasm identity rather than by `ContractExecutable::StellarAsset`.
- **Correctness check**: Compare native and Wasm execution for the generated two-token swap shape, including ledger changes, events, return XDR, auth consumption, failure cases for deadline/amount/min-output/path shape, and refundable/non-refundable resource accounting under the new protocol. Existing Soroban invoke-host-function and parallel-apply tests cover the surrounding bridge/parallel state machinery; add focused equivalence tests for this new native path rather than weakening any existing assertions.
- **Benchmark focus**: Run the soroswap apply-load matrix (`TX=2000`, `T=8`) with multiple non-Tracy runs and verify top-line apply time improves by at least the objective's 3% Medium floor; a successful full native router path should plausibly exceed 10%. In Tracy validation, `Vm::invoke_function_raw` and VM `call` counts/time should drop for swap transactions while C++ `recordStorageChanges`, event encoding, and ledger-change output remain present and consistent.
