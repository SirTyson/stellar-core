## Meta-Patterns

1. **Tracy zones are not production overhead**: Self-time in zones guarded by `#[cfg(feature = "tracy")]` measures profiling instrumentation cost, not soroswap apply-path work. Always confirm that a profiled zone is present in non-Tracy production builds before treating its self-time as an optimization target.

2. **Protocol-visible `const_term` makes charge-count changes infeasible**: In the p26 soroban host, `ValSer` (cpu `const_term=230`, mem `const_term=242`) and `MemCpy` (cpu `const_term=42`) both accumulate as `iterations × const_term + inputs × lin_term`. Any reduction in the number of `charge()` calls directly and observably shifts `cpu_insns`/`mem_bytes`, which are verified by exact-budget tests in `budget_metering.rs` and `e2e_tests.rs`. Batch-construction or skip-serialization optimizations that change the call count are infeasible within a single protocol version.

3. **Aggregate zone time is an upper bound on removable work**: Cited profile self-time for a parent zone (e.g., `extend_current_contract_instance_and_code_ttl`, `invoke_host_function` wrapper, `read xdr with budget`) includes unavoidable first-call work, mandatory protocol-visible charges, and unrelated sub-operations. Must isolate the specific skippable subset via focused instrumentation and confirm it clears the 3% Medium floor before promotion.

4. **Store-local wasmi state cannot be pre-cached**: `wasmi::Linker::instantiate` produces an `InstancePre` that owns a store-allocated instance handle and resolved per-store `Func` objects. All of these are mutable and per-invocation; there is no immutable "instantiation prelude" that the current `soroban-wasmi` API exposes for safe caching across `Store<Host>` instances.

5. **Parallel apply setup is already pipelined with worker execution**: `applySorobanStageClustersInParallel` constructs each `ThreadParallelApplyLedgerState` immediately before launching that cluster's `std::async`. Later clusters' setup is already overlapped with earlier clusters' execution, so the pattern is not an all-setup-before-any-worker barrier. Most `applySorobanStageClustersInParallel` self-time is `std::future::get()` blocking waiting for the slowest worker, not serial construction.

6. **C++→Rust bridge: eliminating serialization still requires Rust decoding**: The soroban host requires native Rust XDR types (`HostFunction`, `AccountId`, `SorobanAuthorizationEntry`). Passing the original on-wire byte slice from the C++ side avoids re-serialization but does not eliminate the Rust `metered_from_xdr` decode or the corresponding `ValDeser` budget charges. "Eliminate the redundant roundtrip" hypotheses must account for the fact that only half the roundtrip (the C++ write) is removable.
