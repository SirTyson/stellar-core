# H001: Native Soroswap Router Exact-Swap Trampoline

**Date**: 2026-05-24
**Subsystem**: transaction-ledger / Soroban host apply
**Severity**: High
**Impact**: soroswap apply-time reduction by removing the remaining top-level router Wasm interpreter path
**Hypothesis by**: gpt-5.5, high

## Expected Behavior

For protocol-next soroswap benchmark transactions that invoke the official router `swap_exact_tokens_for_tokens` entry point with the canonical two-token path and deadline/recipient arguments generated by `ApplyLoad`, stellar-core should produce the same transaction result, auth tree consumption, pair/SAC side effects, events, refundable-fee accounting, and metadata as the Wasm router. The efficient path should recognize this exact router call shape, compute the same output amount and pair call arguments natively, then invoke the already-protocol-gated native pair/SAC path in canonical transaction order rather than instantiating and interpreting the router Wasm for every swap.

All non-canonical router calls, unexpected path lengths, unsupported token/pair layout, or protocol <= p26 must fall back to the current Wasm execution path.

## Mechanism

The current accepted state has native Soroswap pool getter/swap hooks, but `Host::call_contract_fn` still instantiates a VM for the top-level router contract whenever `instance.executable` is Wasm and the called function is not a pool hook. Soroswap apply-load transactions enter the router Wasm first, and only later reach the native pair path through nested calls. The deviation from the ideal soroswap apply path is that deterministic router arithmetic, path validation, and pair-call argument construction still pay the full Wasm `Vm::invoke_function_raw` / host-import dispatch envelope even though the benchmark shape is fixed and already ultimately dispatches to native pair/SAC logic.

A protocol-gated router trampoline would match the router Wasm hash plus `swap_exact_tokens_for_tokens`, decode only the canonical benchmark arguments, reuse existing storage/auth/frame machinery to call the pair `swap` path, and leave all pair/SAC event and storage semantics to the existing native lower-level implementation. This targets the dominant remaining apply-descendant VM zone rather than another post-native micro-optimization inside SAC transfer or pair event construction.

## Trigger

Run `scripts/run_apply_load_matrix.py` for `soroswap, TX=2000, T=8` on the current `CURRENT_STATE.md` baseline. The trigger is the standard apply-load router invocation generated by `src/simulation/ApplyLoad.cpp` for exact-token swaps: a router Wasm call with a fixed two-token path that computes pair output amount and calls the pair `swap` function.

- Source confirms native pool hooks are present (`match_native_soroswap_pool_getter`, `match_native_soroswap_pool_swap`, `call_native_soroswap_pool_swap`) but only checked for pool Wasm hashes in `Host::call_contract_fn`. A router contract still takes the Wasm fallback at `frame.rs:814-824`.
- The current baseline has already accepted native pool getter/swap and native pool raw-instance storage optimizations, so the remaining router Wasm envelope is now a larger relative share of soroswap apply than it was before those lower-level hooks landed.

## Anti-Evidence

- This must not become a broad native fused Soroswap executor that bypasses auth, rollback, TTL, SAC transfer, event, or refundable-resource boundaries. The viable scope is an exact router trampoline that delegates lower-level effects to existing native pair/SAC machinery.
- The official router Wasm is a production contract artifact. A PoC needs a tight allowlist by router Wasm hash, function name, argument shape, and protocol version, plus equivalence tests against the Wasm path for failure ordering and event/auth shape.
- If the router's remaining VM time is mostly mandatory user-Wasm control flow that cannot be safely mirrored from in-tree source, the hypothesis collapses into the previously rejected native-precompile class. The review should distinguish this exact apply-load router trampoline from a general Soroswap precompile.

### Trace Summary

The soroswap apply-load transaction generator constructs a top-level `InvokeContract` call to the router contract function `swap_exact_tokens_for_tokens` with five canonical arguments, then includes router, pair, SAC, trustline, and pair-instance footprint entries plus a source-account auth tree. The p26 host converts that host function into `call_n_internal`, and `Host::call_contract_fn` only recognizes native hooks for the Soroswap pool Wasm hash before falling back to VM instantiation and `Vm::invoke_function_raw` for other Wasm contracts. The current source therefore matches the hypothesis's mechanism, but the fail summary already records the same native router trampoline / fused executor investigation on the native-pool-hook baseline and rejects it as below the objective's Medium threshold.

### Why It Failed

This is substantially the same hypothesis as the already-reviewed native router trampoline / fused executor record. That prior review specifically covered the post-native-pool-hook baseline, measured the remaining router Wasm frame as bounded below 3% of apply time after cluster normalization, and concluded that SAC transfer, native pair swap, reserve mutation, event, auth, rollback, TTL, and metadata work remain mandatory. Under the optimize-soroswap objective, Low or sub-3% projections must be rejected rather than downgraded.

### Lesson Learned

Router-Wasm self-time should not be promoted again without new evidence that the removable router-only portion clears the Medium threshold after active-cluster/critical-path normalization. Preserving consensus-visible semantics leaves the expensive pair/SAC side effects in place, while bypassing them reverts to the already-rejected fused native Soroswap executor class.
