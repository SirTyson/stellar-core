# H001: Native Soroswap router exact-swap executor

**Date**: 2026-05-26
**Subsystem**: transaction-ledger / Soroban native Soroswap apply
**Severity**: Medium
**Impact**: Soroswap apply-time reduction by bypassing the router Wasm frame and its cross-contract dispatch pipeline for the benchmark's recognized exact-swap path
**Hypothesis by**: gpt-5.5, high

## Expected Behavior

When the apply path invokes the official Soroswap router contract for the exact-swap shape used by the soroswap benchmark, the host should recognize the router wasm hash, function symbol, and argument layout, then execute the same ordered pool swaps through a protocol-gated native executor. The executor should preserve transaction determinism, auth preimage ordering, emitted SAC/pair events, storage effects, success hash inputs, and per-transaction result codes, while avoiding the generic router Wasm instantiation/invoke layer and repeated router-to-pool host dispatch.

## Mechanism

The current native fast paths start only after the router Wasm has been instantiated and has issued cross-contract calls to pair contracts. `Host::call_contract_fn` still routes the router itself through `instantiate_vm` and `Vm::invoke_function_raw`, so every soroswap transaction pays one generic router VM frame, generated host-import dispatch, argument relative/absolute conversion, and cross-contract call plumbing before reaching the native pool swap hooks. A protocol-gated native exact-swap executor would decode the router call once, iterate the route in canonical order, and call the existing native pool/SAC helpers directly, removing a broad per-transaction wrapper around the same deterministic swap sequence.

## Trigger

Run the current soroswap apply-load benchmark from `ai-summary/CURRENT_STATE.md` (`soroswap, TX=2000, T=8`) and inspect invocations whose top-level contract id is the Soroswap router and whose function/arguments match the exact-swap path generated by `src/simulation/ApplyLoad.cpp`. These invocations enter `Host::call_contract_fn` as a Wasm executable at the router, then the router calls into native pool swap hooks for each pair.

## Evidence

- The current diagnostic soroswap trace has 71 `applyLedger` windows totaling 4,412.548 ms. Timestamp-filtered events inside those windows show `Vm::invoke_function_raw` at 8,034 calls / 7,231.631 ms inclusive, generated `call` dispatch at 24,078 calls / 4,937.728 ms, `Vm::instantiate_wasmi - instantiate` at 8,079 calls / 464.647 ms, and `SAC transfer` at 16,005 calls / 2,644.783 ms.
- These zones are descendants of `applyLedger`, not TX-set construction: the enclosing C++ path is `InvokeHostFunctionOpFrame doParallelApply` with 8,013 calls / 11,549.175 ms inside the same windows.
- The source already contains protocol-gated native Soroswap pool getter and swap recognition, so the remaining router Wasm frame is a concrete seam rather than a hypothetical precompile framework. The proposed executor would extend the existing hash/function-gated native model upward to the router call shape that drives the benchmark.
- Unlike a narrow router trampoline, the executor would remove the router VM frame and the router's repeated generic cross-contract dispatch into native pair hooks. Even after preserving SAC transfers, event production, auth, and storage mutation, eliminating the router wrapper around every swap plausibly clears the 3% Medium threshold on the current ~207 ms soroswap median.

## Anti-Evidence

- Correctness depends on exact equivalence with the official router Wasm for the matched function and argument shape. If audited source or an exhaustive equivalence harness is unavailable, the PoC should be rejected rather than inferred from opaque bytecode.
- The inclusive `Vm::invoke_function_raw` and `call` timings include mandatory child work that remains, especially pair swaps, SAC transfers, auth, event hashing, and storage effects. The PoC must add narrow spans or counters around the removed router-only portion.
- The optimization must be protocol-gated because it changes Wasm dispatch and budget accounting. Any intentional metering change needs budget-focused tests and next-protocol gating; p26 replay semantics must remain exact.

### Trace Summary

The source path matches the previously investigated native router trampoline/fused executor family. `ApplyLoad::generateSoroswapSwaps` builds top-level `swap_exact_tokens_for_tokens` calls to the router, and `Host::invoke_function` converts those args then calls `call_n_internal`; `call_contract_fn` only recognizes the pair Wasm hash for native pool getters/swaps and otherwise instantiates the router Wasm and enters `Vm::invoke_function_raw`. The prior condensed failure already covers this exact seam after native pool hooks landed: removing the router frame leaves mandatory SAC transfer, pair native-swap, reserve mutation, auth, rollback, storage, TTL, event, and result-hash work, so the normalized router-only savings are below the objective's Medium threshold.

### Code Paths Examined

- `ai-summary/fail/transaction-ledger/summary.md` — records the prior failure for `002-native-router-trampoline-refined.md + 002-fused-native-router-exact-swap-executor.md + 001-native-router-swap-trampoline.md + 001-native-router-exact-swap-trampoline.md`, including the fused native router exact-swap executor variant and the below-threshold rationale.
- `src/simulation/ApplyLoad.cpp:3381-3505` — the benchmark creates one top-level router `swap_exact_tokens_for_tokens` invocation per transaction with a two-token path and the expected router/pair/SAC footprint.
- `src/rust/soroban/p26/soroban-env-host/src/host/frame.rs:782-825` — current native recognition applies only to `SOROSWAP_POOL_WASM_HASH`; router calls miss these checks and use `instantiate_vm` plus `Vm::invoke_function_raw`.
- `src/rust/soroban/p26/soroban-env-host/src/host/frame.rs:1127-1375` and `1465-1500` — the existing native pair swap body and SAC helper calls are the child work that remains necessary under a fused router executor.
- `src/rust/soroban/p26/soroban-env-host/src/vm.rs:155-186` and `393-411` — the removable router VM instantiation and raw invocation mechanics are the same bounded costs cited in the prior failure summary.

### Why It Failed

This is substantially equivalent to the prior native router trampoline/fused executor investigation, including the same top-level router exact-swap shape and the same proposal to bypass router Wasm while preserving the native pair/SAC child effects. The prior review concluded the remaining removable router-only frame is below the optimize-soroswap Medium threshold after critical-path normalization, and the current hypothesis does not add a novel mechanism or stronger severity basis.

### Lesson Learned

For Soroswap router ideas, do not aggregate inclusive `Vm::invoke_function_raw`, generated `call`, or SAC transfer totals as removable. The native router seam must be isolated to router-only Wasm/frame work after subtracting mandatory pair/SAC/auth/storage/event semantics, and that exact fused-executor angle has already been rejected as below threshold.
