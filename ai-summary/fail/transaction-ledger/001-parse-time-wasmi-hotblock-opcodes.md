# H001: Parse-time wasmi hot-block opcodes for Soroswap router and pair execution

**Date**: 2026-05-22
**Subsystem**: transaction-ledger / Soroban VM apply
**Severity**: High
**Impact**: Soroswap apply-time reduction by restructuring the dominant in-apply Wasm execution path
**Hypothesis by**: gpt-5.5, high

## Expected Behavior

For the current next-protocol soroswap apply-load workload, router and pair contracts should execute with exactly the same Wasm semantics, host-import ordering, budget charges, traps, diagnostics, events, and ledger effects as the existing wasmi interpreter. The efficient path should reduce interpreter dispatch overhead only by changing the translated instruction representation inside the pinned wasmi engine, not by replacing contracts with native precompiles or changing any observable host behavior.

## Mechanism

The accepted current trace still spends the bulk of `applyLedger` inside parallel Soroban worker execution: `applySorobanStageClustersInParallel` accounts for **3.427 s** inside `applyLedger` windows, while all 14,000 `invoke_host_function` events are fully contained in those windows. The hottest remaining work is not C++ glue but repeated router/pair Wasm execution, with apply descendants including `invoke_host_function`/`invoke_host_function_or_maybe_panic` at **24.376 s total worker time**, `Vm::invoke_function_raw` at **682.977 ms self**, generated host-function dispatch `call` at **1.126 s self**, and high-frequency budget `charge` at **1.855 s self**.

Prior superinstruction attempts that pattern-matched during interpretation can regress because they add per-instruction overhead to the common path. A parse-time lowering inside the pinned wasmi translator can avoid that failure mode: when `ParsedModule::new_with_isolated_engine` / `wasmi::Module::new` translates the known router and pair bytecode, it can replace only statically matched straight-line hot blocks with deterministic custom opcodes that execute the same original instruction sequence and emit the same fuel/budget settlement points. This materially restructures the dominant `closeLedger` phase while preserving determinism because every node translates the same Wasm bytes to the same opcode stream before execution.

## Trigger

Run the current soroswap apply-load benchmark (`soroswap, TX=2000, T=8`) from `ai-summary/CURRENT_STATE.md`. The trigger is any valid swap transaction generated by `ApplyLoad::generateSoroswapSwaps`: each transaction invokes the router, which repeatedly executes router/pair Wasm and SAC host imports under `applyLedger`.

## Evidence

Timestamp filtering against `applyLedger` windows confirms the relevant zones are in scope: `applyLedger` totals **5.076 s** over 71 windows, `applyTransactions` totals **4.456 s**, `applySorobanStageClustersInParallel` totals **3.427 s**, and all `invoke_host_function` / `Vm::instantiate_wasmi - instantiate` events are inside those windows. The current trace still shows large aggregate worker time in VM execution and generated dispatch even after accepted storage/setup optimizations, while pure C++ phases such as `commitChangesToLedgerTxn`, `recordStorageChanges`, validation, and prefetch are now sub-threshold in the fail log.

This is not a native Soroswap precompile: it does not need audited router/pair source because it executes the original Wasm instruction stream with a different internal opcode representation. It is also not the failed runtime superinstruction shape: the optimization decision happens once at deterministic module translation time, avoiding per-instruction pattern checks in the hot interpreter loop.

## Anti-Evidence

The PoC must work inside the pinned wasmi translator/executor rather than beside `ParsedModule`; the fail log already records that `ParsedModule` holds translated wasmi bytecode, not raw Wasm suitable for external quickening. The custom opcodes must preserve fuel accounting, traps, control-flow edge cases, host import boundaries, and stack effects exactly; if the implementation adds runtime guards to every instruction, it risks reproducing the prior superinstruction regression.

### Trace Summary

The close-ledger path reaches Soroban VM execution exactly as described: `applySorobanStageClustersInParallel` launches cluster workers, each worker calls `TransactionFrame::parallelApply`, `InvokeHostFunctionOpFrame::doParallelApply`, `e2e_invoke::invoke_host_function`, and then `Host::invoke_function`. Wasm contract calls go through `Host::call_contract_fn`, instantiate a `Vm` from the cached `ParsedModule`, and execute `Vm::invoke_function_raw` / `metered_func_call`; host imports cross back through the generated dispatch shim. The proposed parse-time hot-block opcode lowering is the same optimization class as the already-reviewed compile-time basic-block wasmi executor: it changes the pinned wasmi translated instruction stream / executor to reduce interpreter-loop dispatch for straight-line hot code.

### Why It Failed

This is not novel. The specific mechanism — parse/compile-time recognition of hot straight-line wasmi bytecode and replacement with larger executor units to reduce interpreter dispatch — is substantially equivalent to `002-basic-block-wasmi-executor.md`, which was already reviewed and rejected because the attributable pure-dispatch share does not meet the optimize-soroswap Medium threshold after subtracting mandatory host-import body work and normalizing across the configured 8-way parallel apply. It also overlaps the prior `001-wasmi-superinstruction-dispatch.md` final-review lesson: changing wasmi dispatch for hot Soroswap bytecode requires authoritative benchmark proof and previously regressed by 1.8-2.14%.

The traced code supports the prior rejection rather than a new High-severity finding. `Vm::invoke_function_raw` and generated dispatch include mandatory argument conversion, budget/fuel synchronization, host-import calls, trap/error handling, and result conversion; parse-time custom opcodes can only remove a subset of interpreter dispatch between these boundaries. Under this objective, even a technically correct low-level dispatch optimization must clear the 3% Medium floor, and the duplicate prior review already found this class below threshold.

### Lesson Learned

Do not promote new wasmi hot-block or basic-block executor hypotheses unless they supply a genuinely new measured removable component beyond generic interpreter-loop dispatch. Aggregate `invoke_function_raw` or generated `call` totals are not enough; future VM proposals must isolate pure dispatch self-time after excluding host-import body work, budget/fuel settlement, marshalling, and unavoidable call-boundary semantics.
