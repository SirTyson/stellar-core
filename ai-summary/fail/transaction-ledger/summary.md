## Meta-Patterns

1. **Benchmark Warm-up Inflation**: `benchmarkModelTxTpsSingleLedger` includes `warmAccountCache()` before the timed sampling loop. Profiling during warm-up over-counts entry-scan and cache-miss costs that are not part of the steady-state apply window. Always isolate the timed region from setup calls.

2. **wasmi `InstancePre` Is Not Reusable**: Identical to the soroban subsystem finding — the pinned wasmi version's `InstancePre` is store-bound and one-shot. This has been verified at two subsystem levels.

3. **Prefetch Pass Overlap Is a False Claim**: For Soroban-only ledgers, `prefetchTransactionData` builds an empty key set. The two prefetch passes (`prefetchTxSourceIds`, `prefetchTransactionData`) do not overlap in the soroswap shape. Verified from two different hypothesis angles.

4. **Footprint Key Type Matters for InMemorySorobanState**: Classic trustline and account keys in the Soroban tx footprint bypass the `InMemorySorobanState` path entirely. Only CONTRACT_DATA and CONTRACT_CODE keys go through the in-memory Soroban state. Always filter footprint key counts by entry type before estimating call counts.

5. **Sub-Threshold Narrow Fixes**: Several transaction-ledger hypotheses (xdr_size skip, medida histogram disable, recordStorageChanges TTL precompute, CxxBuf precompute, inline argument storage, TransactionMetaBuilder construction, getLiveEntryOpt coalescing, fee/seqnum parallelism) project at 0.2–2.5% individually. These are all below the 3% Medium floor. A combined approach touching multiple of these paths might reach Medium, but each alone does not.

6. **Aggregate Worker Time ≠ Critical-Path Time**: For a T-cluster parallel apply, aggregate worker self-time must be divided by T to estimate the critical-path upper bound. Multiple recent failures (H006 TTL extend, H007 MeteredOrdMap, H002 in-place storage, H002 inline VM args, H002 lazy snapshots) overstated impact by citing aggregate worker time without this division. Always compute critical-path estimates, not aggregate worker totals.

7. **InMemorySorobanState Cache Pressure Can Negate XDR Savings**: Adding pre-serialized bytes or additional cached structures to `InMemorySorobanState` adds resident memory and L1/L2 cache pressure. When the CxxBuf bridge still requires copying bytes into a fresh `std::vector`, the heap allocation overhead is preserved and the cache pressure adds overhead, producing a net regression. Pre-serialized-byte caching in the in-memory state requires a zero-copy bridge path to be beneficial.

8. **BucketList Reporting Walk Cost Is Trivial**: `addLiveBatch` counter walks and per-ledger reporting code accumulate well under 100 µs per benchmark run in the soroswap shape. The large Tracy `addLiveBatch` total is entirely descendant merge work inside `addBatchInternal`. Always measure non-child-zone self-time before targeting counter or reporting code in `addLiveBatch`.

9. **Validation Zone Tracy Trap**: Global `commonValidPreSeqNum` and `checkValid` self-time in apply-load traces includes TX-set construction and flood validation that are outside the measured `applyLedger` window. Always timestamp-filter validation zone events against `applyLedger` before projecting optimization impact.

10. **Protocol-Surface Serialization Compatibility**: Container replacements for types that participate in the on-disk index format or XDR protocol surface (e.g., `BucketEntryCounters`) must still serialize to the original form, which forces iteration at serialization time and typically negates any in-memory layout benefit. Always check protocol compatibility before proposing container replacements.

11. **Soroban Host Internal Micro-Optimizations Are Individually Sub-Threshold**: Budget charge path specialization, per-frame decoded-value caching, and single-borrow object comparison helpers each save a small fraction of apply time. None reaches the 3% Medium floor individually. They also carry correctness risk from Soroban's exact-budget invariants or cross-frame state semantics. Pursue only if a combined approach can aggregate multiple sub-threshold wins into a single protocol-gated change.

12. **`ValSer` Const-Term Prevents Naive Old-Entry Serialization Elimination**: In the p26 metering model, `metered_write_xdr` charges `ValSer` with non-zero `const_term` for every chunk, so replacing recursive old-entry XDR serialization with a stored total byte length changes visible `cpu_insns`/`mem_bytes` and can change budget-exceeded behavior. Eliminating the old-entry XDR write in `get_ledger_changes` is only safe with a protocol-gated metering change or a design that reproduces the exact per-charge accounting without the full XDR traversal.

13. **wasmi Bytecode Is Already Translated at `ModuleCache` Level**: `ParsedModule` wraps `wasmi::Module` whose code-section entries are translated into wasmi bytecode by `Module::new` during module parsing. There is no raw WebAssembly at the Stellar Core `ModuleCache` level to quicken or rewrite locally. Future VM-dispatch hypotheses targeting interpreter overhead must work inside the pinned wasmi translator/executor with narrow measurements of dispatch self-time, not propose a local quickening artifact beside `ParsedModule`.

14. **`FuelConsumptionMode` Is Not a General Lazy Instruction-Fuel Knob**: In the pinned soroban-wasmi fork, `FuelConsumptionMode::Lazy/Eager` only affects when fuel is charged for bulk memory/table operations (grow, copy, fill, data/element init). Ordinary Wasm instruction metering is already block-aggregated into `ConsumeFuel` bytecode inserted during `Module::new` and is unaffected by the mode. Lazy per-instruction fuel accounting would require changes inside the wasmi executor itself.

15. **`get_ledger_changes` Metered Serialization Is Protocol-Visible**: `metered_write_xdr` and `metered_from_xdr` inside `get_ledger_changes` charge `ValSer`/`ValDeser` that contribute to the transaction's visible `cpu_insns`/`mem_bytes`. Skipping these for unchanged read-only entries changes protocol-visible budget totals and is only safe under a protocol-gated metering change. Note also that `extract_ledger_effects` already filters out read-only no-op entries before the C++ `recordStorageChanges` decode, so the claimed C++ win is absent.

16. **Opaque Wasm Binaries Block Native Precompile PoCs**: Implementing a native precompile for a specific contract requires audited contract source plus focused equivalence test coverage to prove correctness on the consensus-critical apply path. When contracts are available only as vendored `include_bytes!` opaque Wasm, a correct native precompile cannot be safely built for production use. The test-native `ContractFunctionSet` scaffold uses an empty-Wasm marker and is gated behind `test`/`testutils`; it cannot be adapted for production hash-keyed dispatch.

17. **Three-Run Benchmark Consistency Is the Final-Review Gate**: An optimization must produce consistent soroswap improvement across all three independent non-Tracy benchmark runs to pass final-review. A single faster run that falls within run-to-run variance, combined with two regressions, does not satisfy the objective's `CONFIRMED` criteria even if the source change builds cleanly and all tests pass. Average-regressing PoCs must be rejected regardless of isolated run improvements.

18. **All Prefetch Phases Collectively Bounded Under ~3 ms/Ledger**: `prefetchTxSourceIds`, `prefetchTransactionData`, and their wrappers together total under ~3 ms/ledger on the soroswap shape. Async pipelining (H003), internal parallelism (H004), and wrapper-skipping (H008) all hit sub-threshold ceilings independently, and the existing collapse-passes failure (H002) confirmed there is no key-set overlap to exploit either. Future prefetch hypotheses must either eliminate the entire prefetch phase and its caller plumbing in one structural change with measured combined saving above the threshold, or target a different code path entirely.

19. **Budget Accumulator Flush Boundaries Are Costly**: A protocol-gated budget charge accumulator that defers per-charge limit checks must flush before host→Wasm returns, resource reporting, shadow sections, and other protocol-visible boundaries. These flush boundaries add overhead that can negate the per-charge savings for the soroswap workload. Benchmark three authoritative non-Tracy runs before claiming that host metering coalescing is beneficial.

20. **Stage Scheduler Redesigns Are Workload-Specific**: Both the DAG scheduler (final-review regression, transactions subsystem) and the wavefront scheduler (no barriers to remove, one stage) failed because the soroswap benchmark generates one Soroban stage per ledger. Stage-count distribution and actual barrier-idle time must be measured on the target workload before investing in scheduler redesigns.

21. **applyOperations Shield Elision Is Soroban-Irrelevant**: In v23+, `applyOperations` is the classic-tx-only apply path; Soroban transactions are dispatched through `parallelApply`. Micro-optimizations to `applyOperations` — shield elision, single-op specialization, per-op LedgerTxn elimination — cannot help a Soroban-dominated benchmark like soroswap.

22. **Native Soroswap Hooks Are Not Present in the Current Tree**: Multiple hypotheses failed because they targeted `try_call_native_soroswap_pool_swap`, `soroswap_pool_invoke_sac_balance`, `soroswap_pool_invoke_sac_transfer`, native router trampolines, or raw pair instance storage helpers that do not exist in the reviewed p26 source. The soroswap apply-load benchmark deploys official Soroswap Wasm contracts and the host only has native dispatch for `ContractExecutable::StellarAsset`. Do not propose optimizations inside these native Soroswap paths until a native implementation lands and is confirmed present in the source tree.

23. **commitChangesFromThreads Ordering Constraint Blocks Streaming and Parallel Folding**: The post-stage fold of per-thread entry maps into the global state must apply thread results in canonical cluster-index order to produce identical `mGlobalEntryMap` state across nodes. This blocks streaming-completion overlap (cannot process thread 5 before threads 0–4 complete) and limits parallel folding savings to X × (T-1)/T, which is below the 3% Medium floor for the current `commitChangesFromThreads` phase size (~7.6 ms/ledger).

24. **Destruction and Deferred Cleanup Phases Are Sub-ms After Data Draining**: When upstream apply phases have already drained heavy data from `TxBundle`, `TxEffects`, `ApplyStage`, and related containers, the residual destruction loop is bounded at sub-ms per ledger (primarily empty container frees and unique_ptr heap frees). Async deferral of these destruction phases adds synchronization overhead that typically exceeds the savings. Measure destruction time explicitly before proposing deferral.

25. **wasmi Engine Uses Shared RwLock During Execution, Not Exclusive Lock**: wasmi `EngineInner::execute_func` holds `self.res.read()` — a shared `RwLock` read guard — for the duration of contract execution; it is not an exclusive lock. Only the module-map mutex (`BTreeMap` lookup, brief) and the stack-pool mutex (stack acquire/release, brief) are exclusive. Multiple workers can execute concurrently on the same engine without serialization. Engine sharding adds memory and rebuild cost without removing actual contention. Always verify the lock mode (shared vs. exclusive) before projecting cross-worker serialization savings.

26. **addLiveBatch → snapshotLedger → bucketListHash Chain Is Mandatory and Synchronous**: `addLiveBatch` in `finalizeLedgerTxnChanges` must complete before `snapshotLedger` because `snapshotLedger` computes the `LedgerHeader.bucketListHash` for the published `CompleteConstLedgerState`. Deferring or async-offloading `addLiveBatch` past `snapshotLedger` requires redesigning how `bucketListHash` is derived and is a consensus-visible semantic change, not a safe optimization. Future bucket-write hypotheses should target internal merge work inside `prepareFirstLevel`/`mergeInMemory`, not the `addLiveBatch` call as an atomic unit.

27. **Post-Cluster Serial Loops May Be Near-No-Ops in Benchmark Configuration**: Loops executed after each parallel Soroban apply stage (e.g., `checkAllTxBundleInvariants`, `maybeSetRefundableFeeMeta`) contain early-out paths gated on `metaEnabled` and invariant-count checks. Under soroswap benchmark configuration (meta disabled, `INVARIANT_CHECKS` empty), these loops short-circuit immediately and cost essentially nothing. Always measure post-cluster loop cost under the actual benchmark config before proposing batch/vectorize optimizations.

28. **Trivially-Inlineable Safety Wrappers Are Not Performance Targets**: Templated safety wrappers such as `LedgerEntryScope` that compile to an 8-byte scope-ID copy plus a forwarded optional add approximately 5 ns per adoption site (~12 µs/ledger at soroswap tx density). Removing them for performance is unjustified — the gain is sub-noise (0.005% of ledger time) and the correctness instrumentation serves as a compile-time parallel-apply safety net. Verify post-inlining assembly cost before proposing removal of any safety wrapper.
