## Meta-Patterns

1. **Already-Tried Paths**: `InMemoryBucketEntry` virtual wrapper replacement has been attempted multiple times on this branch. Do not re-propose the same structural refactor without evidence that the underlying blocker has changed.

2. **Background Commit Work**: `FutureBucket::resolve` and bucket-index creation run on background threads. Improvements to background latency cannot reduce apply time unless there is a confirmed synchronous apply-thread wait on that background work.

3. **Scope Filter First**: Before writing a ledger-subsystem hypothesis, confirm the target zone is a descendant of `applyLedger` in the Tracy trace, not an aggregate process-level hotspot that includes pre-apply or post-apply phases.

4. **Prefetch Path Triviality**: The `prefetchTransactionData` and `prefetchTxSourceIds` paths are no-ops or near-no-ops for Soroban-only ledgers; hypotheses that skip or combine them cannot yield Medium-severity improvements.

5. **Single-Child LedgerTxn Constraint**: `LedgerTxn::Impl::addChild` calls `throwIfChild()` and records a single `mChild`; exactly one active child `LedgerTxn` can exist on any parent at a time. Any fee processing or apply parallelism scheme that requires concurrent sibling `LedgerTxn` instances is architecturally blocked and requires a different state isolation approach.

6. **Cluster State Parallelism: Memory/Cache Effects**: Moving `ThreadParallelApplyLedgerState` construction into `std::async` workers is structurally correct — the global map is read-only under `DeactivateScopeGuard` and futures can remain indexed deterministically. However, concurrent footprint walks and per-thread entry-map reservations add memory allocation and cache pressure that can negate the theoretical overlap benefit, as seen in a regression across three authoritative non-Tracy benchmark runs. Always benchmark the full three-run matrix before claiming a parallelism win of any severity tier.

7. **Cluster Sequential Ordering Is a Correctness Constraint**: Soroban clusters group transactions with true RW state sharing (e.g., soroswap pair contract reserves, token balances updated by each swap). Any proposal to batch or parallelize within a cluster must first prove zero true RW conflicts between the targeted transactions. For soroswap, every intra-cluster pair of txs writes to the same pair contract storage, so intra-cluster batching cannot amortize per-tx Rust host setup.

8. **applyThread Scaffolding Costs Are Sub-Threshold**: Per-tx setup in the applyThread hot loop — `TimerContext` construction, PRNG SHA256 seed derivation, `TxParallelApplyLedgerState` default construction — is each on the order of hundreds of nanoseconds. With ~250 txs/worker/ledger and T=8 parallelism, the full scaffolding overhead per component is ≤375 µs/ledger (far below the 3% Medium floor). Do not propose hoisting or eliminating applyThread scaffolding without a trace showing substantially higher per-component overlap.

9. **Native Soroswap Path Must Be Present Before Optimization**: Multiple hypotheses failed because they targeted native Soroswap router/pair/SAC helpers that do not exist in the p26 source tree. The current soroswap benchmark deploys official Soroswap Wasm contracts; there is no `try_call_native_soroswap_pool_swap`, `soroswap_pool_invoke_sac_balance`, `soroswap_pool_instance_storage_get`, or equivalent native pair/router dispatch. Do not write follow-on native Soroswap optimizations unless the native hook is confirmed present in the source tree under review.

10. **Stage-Wrapper Gaps Are Not Isolatable to Post-Host Merge Work**: `applySorobanStageClustersInParallel` wrapper wall time and end-of-stage gaps after the last `parallelApply` event are dominated by slowest-cluster completion, mandatory RO-TTL flushing, worker teardown, and synchronization overhead. They cannot be attributed to a specific eliminable code path such as dirty-map merge without dedicated per-operation Tracy zones. Always instrument the candidate path before projecting from stage-level wrapper gaps.
