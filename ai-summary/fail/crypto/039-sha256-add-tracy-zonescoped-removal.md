# H039: Remove Per-Call ZoneScoped from SHA256::add Streaming Hot Path

**Date**: 2026-05-21
**Subsystem**: crypto
**Severity**: Low (sub-1%)
**Impact**: apply-time
**Hypothesis by**: claude-opus-4.7, high

## Expected Behavior

`SHA256::add` (`src/crypto/SHA.cpp:62-71`) is the streaming-update entry point
into the OpenSSL SHA256 state machine. For a high-call-count cryptographic
update primitive, the wrapper around `SHA256_Update` should be effectively
free (a single function call plus the openssl update). It should not impose
any per-call instrumentation cost in production builds, and the streaming
form should not be measurably more expensive per byte than the one-shot
`::SHA256()` form already used in `sha256(ByteSlice)`.

## Mechanism

The actual implementation places `ZoneScoped;` at line 65, inside the
streaming `add` call. Every `SHA256::add()` invocation — including the
millions of tiny `XDRHasher::hashBytes` flush callbacks generated by
`xdrSha256<T>(...)` archiver walks — pays Tracy zone entry/exit cost in
Tracy-instrumented builds. The deviation from expected behavior is that the
profiler instrumentation is the dominant per-call self-time on Tracy traces,
inflating the apparent SHA256 cost and biasing optimization decisions. In
non-Tracy production builds the macro compiles away and the overhead vanishes
entirely; the apply-time impact in the actual production build is therefore
zero.

## Trigger

Run `apply-load --mode soroswap` with and without `--enable-tracy`; observe
that `SHA256::add` reports tens of millions of nanoseconds of self-time in
Tracy traces but contributes zero measurable difference between the two build
configurations.

## Target Code

- `src/crypto/SHA.cpp:62-71` — `SHA256::add` body with `ZoneScoped`
- `src/crypto/BLAKE2.cpp` — symmetric `BLAKE2::add` site (same pattern)
- `src/crypto/XDRHasher.h:50-58` — `flush()` calls `Derived::hashBytes()`
  per buffer fill, generating high call counts that flow into `SHA256::add`

## Evidence

The streaming-add codepath is the only SHA256 entry point with a
per-invocation Tracy zone (the one-shot `sha256()` and `subSha256()` forms
also have `ZoneScoped` but fire once per cryptographic operation, not once
per chunk). H012/H023/H026/H029/H035 collectively rejected SHA256
optimization at the streaming-class boundary; this hypothesis isolates the
Tracy-overhead portion specifically.

## Anti-Evidence

The total SHA256 in-apply budget for soroswap is ~4.17 ms per ledger
(~0.67% of the 621 ms median apply window) per Meta-Pattern 1. Removing
the `ZoneScoped` line affects only Tracy builds; non-Tracy production
benchmark numbers are unchanged because the macro is a no-op in the
release build. The current baseline (`CURRENT_STATE.md`) was measured
without `--enable-tracy` for the verdict numbers; the optimization has no
production apply-time impact.

## Review

**Verdict**: NOT_VIABLE
**Date**: 2026-05-21
**Failed At**: hypothesis
**Novelty**: PASS — Meta-Pattern 7 acknowledges the inflation effect but no
prior hypothesis proposes removing `ZoneScoped` from the SHA256/BLAKE2
streaming primitives directly.

### Why It Failed

Tracy `ZoneScoped` macros are no-ops in the non-Tracy production build that
generates the authoritative apply-time numbers. The non-Tracy build's
SHA256 budget is already ~0.67% of apply (Meta-Pattern 1). Removing the
ZoneScoped line would only affect Tracy diagnostic traces, not the headline
benchmark. The change cannot move the verdict metric.

### Lesson Learned

Optimizations that target Tracy instrumentation inflation must produce a
non-Tracy build improvement to count for this objective. When a per-call
Tracy zone shows millions of events, the right response is to size proposed
savings against non-Tracy benchmarks (per Meta-Pattern 7), not to remove the
macro and claim a Tracy-only win.
