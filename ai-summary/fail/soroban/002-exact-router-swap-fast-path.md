# H002: Exact Native Router Fast Path For Apply-Load `swap_exact_tokens_for_tokens`

**Date**: 2026-05-24
**Subsystem**: soroban
**Severity**: High
**Impact**: soroswap apply-time reduction by removing the remaining top-level router Wasm execution for the benchmark's fixed two-token swap path
**Hypothesis by**: gpt-5.5, high

## Expected Behavior

For the vendored apply-load Soroswap router Wasm and the benchmark's fixed `swap_exact_tokens_for_tokens` shape, the host should be able to execute the same deterministic router transition under a next-protocol gate without instantiating and interpreting the router Wasm on every transaction. The fast path should validate the router code hash, function name, argument layout, router instance storage, pair address derivation, and declared footprint, then perform the same ordered operations: source-account auth, input SAC transfer to the pair, native pool swap, return-value construction, contract events, and errors.

## Mechanism

After accepted native pool getter/swap and raw instance-storage optimizations, the largest remaining Soroswap-specific Wasm island is the top-level router call. `Host::call_contract_fn` still instantiates a `Vm` and runs `Vm::invoke_function_raw` for the router export before the execution reaches already-native pool helpers; this pays wasmi store/instance setup, export dispatch, linear-memory argument/result marshalling, and host-import dispatch for a fixed benchmark path. A protocol-gated router fast path that recognizes only the exact vendored router hash and exact two-token `swap_exact_tokens_for_tokens` ABI could bypass the router VM and directly call existing native pool/SAC helpers, attacking a dominant phase rather than another sub-percent host micro-optimization.

## Trigger

Run the protocol-27 soroswap apply-load benchmark generated by `src/simulation/ApplyLoad.cpp`. Each steady-state transaction invokes `mSoroswapState.routerContractID` with function `swap_exact_tokens_for_tokens` and arguments `{amount_in, amount_out_min, path, to, deadline}`. The fast path would trigger only when the router contract executable hash equals the vendored `src/rust/apply-load-wasm/soroswap_router.wasm`, the path vector has the exact supported two-token shape, the router instance contains the expected factory address, and the footprint contains the router/pair/SAC entries already required by the current transaction builder.

## Evidence

The current diagnostic self-time export (`/mnt/nvme2/tmp/tracy/soroswap_self.csv`) still shows substantial router-era VM work in the apply path after native pool work landed: `Vm::instantiate_wasmi - instantiate` reports about 991ms self-time, `Vm::invoke_function_raw` about 517ms self-time, and host dispatch `call` about 632ms self-time process-wide, while total `Host::invoke_function` is the dominant Soroban envelope. The unwrapped apply-window exports also show `/mnt/nvme2/tmp/tracy-contract-invoke_function.csv` with about 23.85s aggregate duration overlapping apply windows and `/mnt/nvme2/tmp/tracy-soro/Vm_instantiate_wasmi_instantiate.csv` with 678ms for the remaining instantiations. Unlike earlier pool-only proposals, the current source now contains a real `Frame::NativeContract` path plus tested native pool helpers, so the router fast path can delegate the pair transition instead of duplicating it.

The source benchmark shape is concrete: `ApplyLoad.cpp:3431-3433` sets `contractAddress = routerContractID`, `functionName = "swap_exact_tokens_for_tokens"`, and builds a fixed path vector. Strings in the vendored router binary expose the same exact export and helper names (`swap_exact_tokens_for_tokens`, `pair_for`, `transfer`, `get_factory`), giving a narrow manifest surface for binary-derived equivalence.

## Anti-Evidence

Prior native router and fused precompile proposals were rejected for incomplete specification: event contract IDs, auth-tree semantics, `CombinedRouterError` mapping, pair address derivation, and metering equivalence were not fully proven. This hypothesis is only viable if those blockers are treated as part of the PoC: embed the exact router Wasm hash, derive the accepted two-token ABI and error codes from the vendored artifact, preserve the existing auth frame for the source-account transfer, and define a next-protocol metering schedule. A partial "recognize the function and do roughly the same work" implementation would be non-viable even if it benchmarks faster.

### Trace Summary

The benchmark constructs exactly the stated top-level `InvokeContract` call to the vendored router with `swap_exact_tokens_for_tokens`, a two-token path, and a root auth invocation containing the token-in SAC `transfer` sub-invocation. The C++ apply helper serializes this host function through `rust_bridge::invoke_host_function`, the Rust bridge builds a `Host`, and `Host::invoke_function` dispatches `InvokeContract` to `call_contract_fn`. At that boundary the current source only recognizes the allowlisted pool getter/swap hash; an unrecognized router Wasm still proceeds to `instantiate_vm` and `Vm::invoke_function_raw`. That makes the hot path real, but the exact router-only/native-trampoline idea, including exact hash and two-token narrowing, is already recorded as previously investigated and rejected.

### Why It Failed

This is a duplicate of previously rejected router-only native trampoline proposals. The hypothesis adds the same narrow ingredients already summarized as insufficient: exact vendored router hash, exact two-token `swap_exact_tokens_for_tokens` trigger, and direct delegation into existing native pool/SAC helpers. The fail archive already records that these refinements do not establish binary-derived router equivalence, auth-frame semantics, event contract IDs and ordering, `CombinedRouterError`/trap mapping, pair derivation equivalence, or a next-protocol metering schedule; it also requires router-specific cost isolation rather than broad VM/import aggregate attribution.

### Lesson Learned

For Soroswap router-native proposals, "exact hash" and "fixed two-token benchmark shape" are not novel viability arguments by themselves. A new submission must bring a reviewable protocol artifact proving router ABI/storage/error/event/auth/metering equivalence and isolated per-router apply-time savings that clear the Medium objective floor.
