**Date**: 2026-05-22
**Subsystem**: soroban
**Severity**: High
**Impact**: Soroswap apply-time reduction by replacing the fixed router -> pool -> SAC transfer stack with one protocol-gated native transaction-shape precompile
**Hypothesis by**: gpt-5.5, high

## Expected Behavior

For protocol-next ledgers, the exact apply-load Soroswap swap shape generated by `ApplyLoad::generateSoroswapSwaps` should produce the same transaction result, ledger writes, contract events, authorization consumption, and deterministic error behavior as the current Wasm path. The optimized path should trigger only when the top-level router hash is `4c3db3ebd2d6a2ab23de1f622eaabb39501539b4611b68622ec4e47f76c4ba07`, the pair hash is `18051456816b66f12e773a56f77c5794fac1b1fb7ab6e22d4fad5a412770f73e`, the export is `swap_exact_tokens_for_tokens`, the args match the benchmark two-token shape, and the footprint/auth tree match the generated transaction. Any mismatch should fall back to the existing Wasm + SAC path.

## Mechanism

The current path instantiates and interprets the router Wasm, invokes the pool Wasm, and then calls built-in SAC `transfer` twice for a transaction shape that is fixed by the benchmark: amount-in 100, minimum-out 0, path length 2, recipient source account, and `UINT64_MAX` deadline. A next-protocol native precompile can consume the same source-account auth node, compute the pair swap sequentially in the same order, directly update the two user trustlines, two pool SAC balance entries, and pair instance reserves from the declared footprint, then emit the same SAC and pool events. This removes the router/pool VM frames and the generic SAC host-object transfer machinery while preserving the existing NUM_CLUSTERS cluster ordering and deterministic per-tx output.

## Evidence

The diagnostic trace confirms all target work is inside `applyLedger`: `Vm::instantiate_wasmi - instantiate` at `soroban-env-host/src/vm.rs:171` has **827,245,199 ns self-time over 14,040 calls**, `Vm::invoke_function_raw` at `soroban-env-host/src/vm.rs:400` has **12,652,494,561 ns total-time over 13,983 calls**, and `SAC transfer` at `stellar_asset_contract/contract.rs:212` has **2,326,747,229 ns total-time over 13,976 calls**. The apply-load source fixes the shape tightly enough to avoid an open-ended native Soroswap implementation: the precompile validates the exact code hashes, two-token path, arg constants, footprint order, and single token-in transfer auth subtree before doing any native work.

This is narrower than a generic router/pair native contract and broader than the previously under-specified pool-only shim: it removes the current dominant stack as one semantic unit and can verify equivalence against the exact generated ledger. Because the current accepted native getter result improved soroswap by 8.13% while removing only getter frames, eliminating both remaining Wasm frames plus the generic SAC transfer machinery is plausibly High if the byte-equivalence harness passes.

## Anti-Evidence

This is high-risk and must be next-protocol gated. Prior native Soroswap hypotheses failed when they left storage schema, event order, error mapping, auth-frame semantics, or metering to later interpretation; this PoC must derive those from the vendored binaries and from a forced-Wasm transcript of the exact apply-load setup. It also intentionally changes metering for protocol-next, so it needs a deterministic fixed schedule or explicit per-operation charges that are documented and tested; p26 behavior must remain untouched.

### Why It Failed

This is a duplicate synthesis of previously investigated native Soroswap bypasses rather than a novel hypothesis. The prior full router/pair bypass already covered replacing known-hash router and pair Wasm execution with a protocol-gated native path; the prior router-only and pool-only records covered the same fixed `swap_exact_tokens_for_tokens` router shape and allowlisted pool `swap` target individually. The current file adds a broader fused boundary that would also bypass generic SAC transfer machinery, but it does not resolve the retained blockers: exact binary-derived router/pool storage and event semantics, error/trap mapping, root and sub-invocation auth-frame behavior, event attribution/order, deterministic rollback behavior, and a next-protocol metering schedule. It also still relies on aggregate VM/SAC timing rather than new isolated, cluster-normalized measurements proving that the additional fused SAC/direct-ledger portion clears the objective's Medium/High threshold after mandatory storage/auth/event work is accounted for.

### Lesson Learned

Do not resubmit native Soroswap router/pool/SAC bypass variants by widening or narrowing the fused boundary unless the proposal completes the retained refinement requirements: binary-proven storage/event/error equivalence, an explicit native frame/auth/event/metering design, forced-Wasm byte-equivalence criteria, and code-hash-specific benchmark attribution that isolates removable apply-path work after NUM_CLUSTERS normalization.
