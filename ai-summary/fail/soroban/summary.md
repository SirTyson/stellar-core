## Meta-Patterns

1. **Parallel Thread State Setup Is Measured Noise**: Serial `ThreadParallelApplyLedgerState` construction before each async worker has been investigated four times across multiple PoC attempts. All passed tests but failed the benchmark gate. Do not re-propose parallelizing this path without a new measurement showing setup cost is now dominant.

2. **Prefetch Redundancy Is a False Claim for Soroswap**: `prefetchTransactionData` and `prefetchTxSourceIds` do not overlap for Soroban-only ledgers. `prefetchTransactionData` builds an empty key set for soroswap-shaped transactions; confirmed upper bound is 0.68% (below the 1% noise floor). Any hypothesis claiming redundancy must trace actual key sets before writing.

3. **wasmi `InstancePre` Is Not Reusable**: The pinned wasmi version's `InstancePre` is store-bound and one-shot. Any VM instantiation caching hypothesis must use the wasmi API correctly. Do not propose `InstancePre` caching.

4. **XDR Bridge Cost Is Distributed and Sub-Threshold**: C++/Rust XDR bridge preparation (`toCxxBuf`, `addReads`) for soroswap is a real but distributed cost that totals well below the 3% Medium floor. Caching encoded bytes in `InMemorySorobanState` or at TransactionFrame construction time have both been evaluated and rejected.

5. **SHA256 / TTL Key Budget Ceiling**: The entire in-apply SHA256 budget for soroswap is ~0.67% of apply time. Any hypothesis that only reduces SHA256/TTL-key recomputation is structurally below the 1% Low floor. Do not write SHA256-only hypotheses.

6. **Async With Immediate Join Is Neutral**: Moving work to `std::async` and immediately `get()`ing the future has zero wall-time benefit. Async offload only matters when the join is deferred past independent work on the original thread; even then, `addLiveBatch` total at 1.3% is below Medium.

7. **Classic-Tx Medida Is Not On Soroswap Hot Path**: The soroswap apply-load generates only Soroban transactions into the parallel Soroban phase; `applySequentialPhase` is never entered. Any classic-tx medida or timer overhead seen in Tracy comes from setup ledgers, not the measured apply window.

8. **Apply-Load Pre-Resolves Bucket Futures Before Timer**: The model-tx benchmark calls `resolveAllFutures()` before reading `timeBefore` and calling `closeLedger()`. FutureBucket::resolve time visible in Tracy is not apply-time savings.

9. **Host Output XDR Cannot Be Skipped Without Metering Change**: `metered_write_xdr` charges `ValSer` with a nonzero `const_term` per write call. Any bulk charge replacement drops `(N_writes-1)*const_term` — a protocol-visible change. A counting-writer approach that preserves exact metering addresses correctness but eliminates the performance benefit (old-entry buffer materialization savings are below noise once serialization work must still run).

10. **Check Source and Git History Before Writing PoC**: If the claimed inefficiency may have been addressed previously, verify in both the current source and git history. `002-remove-inmemory-index-lookup-allocation.md` demonstrates the cost of proposing an already-implemented optimization.

11. **Budget Charge Accumulator Needs Exact Rounding, Not Input Summation**: Aggregating `(iterations, input_sum)` across multiple `charge` calls changes linear rounding totals for variable-input costs (`MemCpy`, `ValSer`, map/vector accesses). Any accumulator design must track per-call already-rounded amounts or scaled residuals, not raw input sums. Additionally, pending charges require mandatory flush points before fuel transfer, public budget observer calls, shadow-mode accounting, and metered-XDR failure paths.

12. **InMemorySoroban State Is the Fast Path for Soroban Keys in Parallel Apply**: `CONTRACT_DATA`, `CONTRACT_CODE`, and `TTL` keys during parallel apply are served from `InMemorySorobanState`, not from the live BucketList snapshot. Bucket-scan hypotheses targeting Soroban footprint reads in the parallel phase are investigating the wrong code path; the BucketList scan hot path is classic (fee/source/account/trustline) reads during `processFeesSeqNums` and non-Soroban fallback reads.

13. **Pool-Only Native Precompile Is Viable but Under-Specified**: A pool-only native Soroswap precompile (targeting the allowlisted pool Wasm hash while keeping the router on its existing path) is a distinct and narrower proposal from the full router/pair bypass. The hot path is real, but any native precompile proposal must specify the exact native export set, storage schema, event order, error/trap mapping, and next-protocol metering schedule before PoC. Normalize aggregate VM time by cluster count to determine the per-stage ceiling.

14. **Sub-Millisecond apply-Thread Serial Paths Are Exhausted**: Multiple soroban-subsystem hypothesis paths that are strictly serial on the apply thread — commitChangesToLedgerTxn (0.14%), getAllEntries (0.083%), addAnyContractsToModuleCache (0.03%), SorobanNetworkConfig loadFromLedger (0.02%), requiresSequentialPreParallelApply probes (~0.4%), SignatureChecker construction per Soroban tx (~0.033%), getNewestVersion short-circuit (~0.48%), serial-tail Histogram::Update (~0.99%) — have each been evaluated and rejected. Combined these total well under 2% of apply time. Do not propose micro-optimizations to these serial paths without a new trace showing substantially higher per-ledger overlap.

15. **All Native Soroswap Bypass Variants Share the Same Unresolved Specification Blockers**: More than a dozen separate proposals (full router+pair bypass, router-only trampoline, pool-only precompile, fused router+pool+SAC, SAC subcall fusion, inline balance reads, pool swap+deposit+withdraw, binary-hash-specified pool swap, exact router plan, two-token trampoline) have been submitted and rejected at reviewer stage. All share the same retained blockers: absent native frame/helper implementation in the current source tree, unspecified binary-derived storage schema, event order, error/trap mapping, auth-tree semantics, and next-protocol metering schedule. Naming exact vendored Wasm hashes, narrowing trigger shapes, or widening fusion boundaries does not resolve any of these blockers. Do not re-submit a native Soroswap bypass variant without completing binary-proven semantic/metering equivalence and a full native-contract protocol specification.

16. **Budget Charge Coalescing Is Exhausted Post-VisitObject/ValSer Success**: After the accepted protocol-gated `VisitObject`/`ValSer` charge coalescing result (success #1), `BudgetImpl::charge` self-time has been reduced to ~1.43% of the soroswap baseline. Even fully eliminating all remaining charge calls cannot clear the 3% Medium floor. Future budget-metering hypotheses must demonstrate multi-percent impact through structural charge-elimination (removing entire charge categories) rather than per-call overhead reduction or accumulator batching. Any remaining accumulator hypothesis must provide a new cost-type distribution showing the eligible constant-cost subset alone clears 3%.
